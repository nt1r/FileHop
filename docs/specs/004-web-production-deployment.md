# Spec 004：Web 生产部署与发布

状态：已确认，待实现。本文为 Web 生产部署与发布的权威需求、技术契约与验收依据；仓库公开、保护规则及发布配置均不得因本文已确认而视为已完成。

关联：[产品基线](../product.md) · [路线图](../roadmap.md) · [Spec 001](001-desktop-text-loop.md) · [Spec 002](002-desktop-file-transfer.md) · [Spec 003](003-server-file-management.md)

本文件为本切片唯一 Spec，尚未创建远程 Issue。

## 1. 目标与范围

将桌面 Web 和后端部署到现有 ARM64 Oracle VPS，通过正式 HTTPS 域名提供 Spec 001–003 的能力。GitHub 托管 runner 完成 CI 和版本产物发布；操作者在 VPS 手动执行部署脚本，不由 Actions 远程推送或自动部署。

不包括 Android、self-hosted runner、自动回滚、备份恢复、高可用、零停机更新、监控平台或自动扩容。接受短暂维护窗口，共享宿主资源可能使开发影响生产性能。

## 2. 已确认的环境与入口

- 开发者远程连接当前 VPS；开发和生产应用同机但使用不同 Compose 项目、账户、会话、密钥、数据库和文件目录。
- 正式域名为 `transfer.hammerbilly.top`；开发域名使用独立的 `transfer-dev`，完整 FQDN 在部署配置中填写。
- 一个独立 Caddy 入口管理两域名，独立持久保存配置及证书数据，不随日常应用更新重建。
- 开发路由转发开发前端和 API，保留独立 Basic Auth；生产路由提供构建后的静态资源并转发生产 API，不继承开发 Basic Auth。
- 浏览器正常流量只使用 HTTPS/WSS TCP 443。Oracle Cloud 控制台网络规则放行 TCP 443，不开放 TCP 80；不要求修改宿主防火墙，也不擅自修改既有 SSH 管理入口。
- 不承诺 HTTP 自动跳转：80 不开放时，用户须直接访问 HTTPS。HTTP/3 所需 UDP 443 不在本版开放要求内。
- 端口监听、容器映射、现有宿主规则及 Oracle 网络路径仍须验证；云端放行不等于服务已可达。
- 后端与开发前端不发布公网端口，SQLite 无独立容器，生产不运行前端开发服务器。
- 容器内保持 `/data/database/transfer.db`、`/data/files`、后端 `0.0.0.0:8080`；宿主挂载区分开发与生产。

## 3. GitHub 与分支流程

- 代码仓库 `nt1r/FileHop` 决定公开，实施公开前检查完整 Git 历史及已发布文件中的敏感内容，并选择许可证。真实泄露凭证须撤销/轮换，不能仅删除当前文件。
- 开源许可证选择 Apache License 2.0（SPDX：Apache-2.0），替代此前 AGPL-3.0 选择。正式许可文本及必要声明在公开发布前落实，不要求衍生作品或网络服务公开源码。
- GitHub 仓库与 GHCR 后端镜像、前端静态制品均决定公开，可见性分别配置，不假设自动同步。公开产物不得包含账户、密钥、数据库或用户文件。
- 分支名称固定为 `dev`，不是 `develop`；GitHub 默认分支为受保护的 dev，日常 PR 默认面向 dev，创建时仍须核对目标。main 保持正式版本发布分支，发布 PR 显式指定 dev → main。
- 个人开发分支经 PR 进入 dev；dev 经发布 PR 进入 main；只有本仓库 dev 可作为合并 main 的来源。
- dev 和 main 禁止直接推送、强推与删除，变更通过 PR 及必需检查；管理员绕过规则也需显式审查，不宣称仅有 workflow 即完成保护。
- main 是版本发布分支，通过版本 tag 选择对应提交构建产物。
- 分支及 tag 规则在 GitHub 配置，记录实际生效的规则与权限；公开仓库仍需核实所用规则功能。

## 4. CI、产物与手动部署

### GitHub 托管 CI

- 所有 CI 检查及正式构建运行在 GitHub 托管 runner；生产 VPS 不安装 Actions runner，不承担 CI 编译。
- PR 执行检查测试，合入 dev/main 后按需复核；版本 tag 触发发布构建，不自动上线。
- 目标产物为 linux/arm64。优先使用仓库可用的标准 ARM64 runner；可用性在实施时验证，不默默切换到付费 larger runner。必要时评估交叉构建或 QEMU。
- 缓存 Cargo 下载/兼容编译产物、前端包管理器下载内容和 Docker BuildKit 层。区分工具链、架构、锁文件及信任边界。
- 冷缓存必须构建成功；缓存不是发布制品仓库，不存真实凭证或生产数据。不承诺零依赖下载或无限缓存空间。
- 外部 PR 不获取发布密钥，不使用 pull_request_target 执行不可信 PR 代码；PR 构建不能污染被特权发布盲目信任的缓存。
- 构建、检查默认只读权限；仅发布步骤有必要的 packages 写权限。正式发布不执行来自未验证提交的任意脚本。

### GHCR 发布

- 使用 GHCR 保存正式产物，后端 ARM64 镜像和前端静态产物由同一 Git 提交构建。
- 前端打包为静态制品镜像，部署时提取到宿主版本目录，Caddy 只读提供，不增加常驻前端服务。
- 发布版本使用 `vMAJOR.MINOR.PATCH`；tag 对应提交必须可验证地属于 main 历史，禁止移动既有发布 tag 或覆盖已经完成的版本发布。
- 发布清单记录版本、Git SHA、目标架构、前后端镜像 digest、清单格式版本、部署工具兼容范围、API 兼容版本及迁移说明。按 digest 部署，不依赖 latest 或仅凭可变镜像标签。
- 同一发布包含来自该 Git SHA 的生产 Compose 描述、配置变量说明和迁移入口约定，并记录部署描述文件的校验和。校验和保证内容一致性，不冒充独立的签名认证；获取来源仍须是受信任的本仓库发布渠道。
- GHCR 后端镜像和前端静态制品公开，VPS 匿名拉取，不配置生产拉取凭证；Actions 发布仍使用最小权限认证。发布前核查镜像层及静态产物没有敏感运行数据。
- 发布清单存放于对应 GitHub Release，所有必需镜像上传并校验后才发布完整清单；半途失败的构建不能被部署脚本视为可部署版本。
- 不自动删除生产正在引用的镜像 digest；清理策略必须保留当前发布产物，不将此等同于回滚能力。

### 手动部署

- 提供类似 `./scripts/deploy.sh v0.1.0` 的明确入口，由操作者在 VPS 主动执行。
- Actions 不持有 VPS SSH/部署凭证，不主动向 VPS 发请求，不调用部署脚本；VPS 主动拉取发布清单与产物。
- 部署脚本不从未知分支下载并执行任意 shell，不重新编译代码，不把版本参数作为 shell 片段执行。
- 部署入口从独立、受控的运维目录运行，不依赖当前 dev 工作区。操作者显式安装并审阅兼容版本的部署工具；脚本校验清单格式及自身兼容范围，不自动替换并执行远端新脚本。
- 使用该发布绑定且通过校验的生产 Compose 描述，显式指定生产项目名、工作目录、配置文件及绝对挂载路径，不从 shell 当前目录或开发默认配置推导。运行密钥仅由 VPS 本地配置提供，不进入发布产物。
- 取得本机部署锁，验证发布清单、目标 ARM64、版本及 digest，再下载产物；阶段和结果持久记录。
- 构建与下载尽量不占维护窗口；维护前失败不改变当前版本，不中断业务。
- 确认生产维护入口已生效后暂停新的业务请求，给予既有传输有限退出时间，超时可中断，由 Spec 001–003 的结果确认与恢复规则处理。
- 停止旧后端后，用清单指定 digest 的目标后端镜像运行约定的迁移命令，不调用开发工作区程序，不让新旧后端同时写一个数据库；启动新版本并通过内部检查，切换同版前端后再开放业务。
- 后端恢复尚未完成时不能接收新上传。正常进程重启中仍允许的读取能力与首次发布开放时机分开设计，不把存活误当成完全就绪。
- 迁移或切换后失败保持维护，不自动回滚、不自动清库、不反复盲跑迁移；保留数据和诊断，由人工处理。
- 暂不提供回滚脚本或旧数据库兼容承诺，不要求操作者为了本版建立备份恢复能力。

## 5. 已确认的技术契约

### 入口、网络与证书

- 共享 Caddy 连接两个隔离应用网络，使用显式不同的开发/生产代理别名，避免两个 backend 在同一入口的解析范围内产生歧义；应用内仍可保留 backend 服务名。
- 仅 Caddy 发布 TCP 443。开发服务不加入生产数据网络、不挂载生产目录，Caddy 不需要读取数据库或上传文件目录。
- Caddy 禁用 HTTP-01，使用受支持 ACME 发行者的 TLS-ALPN-01 经 443 验证；禁用不适用的 HTTP 跳转监听。若域名前存在 TLS 终止代理/CDN，不假设 ALPN 可透传，须调整方案后验证。
- 核实 A/AAAA、OCI 网络规则、宿主可达性及 CAA 等相关 DNS 条件；证书失败不能用忽略证书校验作为正式解决方案。
- Caddy 证书卷持久化，更新配置先校验再 reload；共享入口重启会影响两个环境，此边界需写入运维说明。

### 分支与可信发布

- 必需检查验证 main PR 的来源仓库和分支均符合 dev → main，检查逻辑由可信版本执行，不任由 PR 改写检查使自己通过。
- 长期 dev → main 发布建议保留合并祖先关系，避免反复 squash 造成历史分叉；合并策略在配置说明中固定。
- 发布 tag 使用规则限制创建者与修改/删除。tag 解析后的确切提交必须在 main 的 first-parent 发布序列上，不允许选择仅通过合并进入历史的中间提交；允许为该序列上的旧提交发布尚不存在的新版本，但不提供生产降级能力。
- tag workflow 仅作最小请求入口，不能将其对自身的校验当成独立安全边界。采用独立受保护的发布准入 workflow（从受保护默认分支 dev 的版本运行，例如受约束的 workflow_run 入口），重新查询 GitHub 上的 tag、事件仓库及 main 历史，不信任上游产物携带的校验结论。
- 准入要求事件来自本仓库合法 tag，记录解析后的确切 SHA；在执行目标代码前验证 first-parent 归属与版本未发布，并在最终发布前再次检查 tag 未变化。只读准入步骤不得执行目标提交脚本或下载后执行上游任意脚本。
- 对该确切 SHA 在无发布写权限的 GitHub runner 中重新执行所需检查及构建，不借用其他 SHA 的检查结果；失败或未完成时不发布。构建完成后的独立发布 job 才取得最小 packages/Release 写权限，只消费本次受控运行的指定产物，不执行产物中的代码。
- 默认分支 dev 上的准入 workflow 及第三方 Actions 是信任根，变更须走受保护 PR 并人工审阅。tag 入口本身运行于仓库 Actions 权限体系内，因此必须同时限制 tag 创建者；本方案不宣称能够抵御拥有规则绕过或任意 workflow 修改权限的管理员。
- 同版本发布串行且不能覆盖已发布清单；PR 检查可取消过时任务，已经开始发布产物的任务不盲目被后续事件取消。
- runner 镜像、Actions 版本、Rust 工具链、Node 与包管理器版本固定或明确记录，第三方 Actions 优先固定到完整提交 SHA。

### 发布切换与维护

- 前端按版本目录存放，index 与带内容哈希资源配套；维护解除前切换到新版本，不暴露半提取产物。发布元数据和 index 不使用会掩盖版本切换的长期缓存。
- 前后端同版只描述服务器产物，不假设已打开页面自动更新。前端内置发布标识与 API 兼容版本，后端提供无敏感信息且禁止缓存的版本查询，返回发布标识及支持的 API 兼容范围。
- 页面从维护恢复、重新回到前台或准备恢复上传队列时先检查兼容性；普通 API 也须能拒绝不兼容客户端，不能仅依赖一次版本检查。已开始的请求沿用原有提交/未知结果规则。
- 不兼容时停止新的业务写入和自动上传接续，提示需要刷新；保留页面内草稿及队列，允许复制文本，说明刷新会丢失未持久化内容。不得强制刷新或生成新发送标识悄悄重发。
- 为不兼容旧客户端保留最小稳定控制契约：无敏感信息的版本查询、Web/原生登录与会话检查、已有发送/尝试状态查询、停止未提交上传及退出登录。登录继续验证密码、限流及对应客户端安全规则；需要凭证的控制操作仍鉴权并遵守原幂等规则，不要求匿名版本查询先登录。
- 旧客户端凭证到期后可通过稳定登录路径取得凭证来确认或终止已有任务；这不恢复业务兼容性，服务端仍拒绝其新文本发送、新上传准备及其他不兼容业务操作。客户端保留更新提示和输入，不因登录成功自动恢复业务队列。变更控制契约须先另行设计升级路径。
- 兼容的旧页面可继续使用，不要求每次发布都刷新；若旧页面加载延迟资源失败，应提示刷新而不是清空草稿。保留旧产物目录不等于承诺自动回滚。
- 维护响应返回明确 503 与 Retry-After，不能被客户端误判为认证失效或确定发送失败。前端不丢弃内存草稿/队列。
- 限时退出与后端优雅关闭、上传清理协调；停止进程后再启动迁移任务，不强行释放尚未核实清理的额度。
- 每次迁移使用可追踪的 schema 版本，失败不标记成功；是否可重试依据数据库实际状态，不承诺所有迁移均可无条件事务回滚。
- 部署锁与维护状态跨脚本异常退出有可检查记录；人工可查询当前阶段，恢复操作不能默认再次破坏性执行已完成步骤。
- 维护仅作用于生产站点，开发域名的路由与 Basic Auth 不变。使用持久维护状态及重启时默认保持关闭的入口配置；Caddy reload、重启或脚本异常退出不能自动解除维护。
- 维护开关的生成配置先校验，持久记录与运行入口须一致。只有确认生产入口已阻止新业务请求，才允许停旧后端或迁移；任何不确定状态停止后续破坏性步骤并人工核实。
- 新后端通过本机或受控内部网络进行健康和恢复就绪检查，不依赖被维护页面阻挡的公网业务接口，也不为此开放公共绕过路径。
- 只有部署检查通过后显式解除维护并记录当前发布；解除失败维持或重新确认为维护状态，不把脚本退出当作上线成功。故障期间既有长连接按退出时限处理，不声称维护能撤销已接受请求。
- 正式启动先验证存储目录身份和配置，禁止因错误挂载而静默初始化一个替代空生产数据库。
- 首次部署必须显式调用 Spec 001 初始化命令，使用目标版本镜像及明确的生产挂载创建数据库、存储标识和唯一账户。普通启动/升级只验证并使用已有实例；空目录不自动视为合法首次安装，部分初始化失败保留诊断并拒绝自动覆盖。

### 最小运维能力

- 健康检查区分存活、数据库可用、文件恢复/上传就绪。详细内部检查仅用于受控网络或本机，公网不泄露配置路径。
- 应用重启策略、容器日志轮转、错误日志和当前发布标识可查询；健康检查变为 unhealthy 不等于 Docker 自动重启，具体策略在部署说明中解释。
- 不记录正文、密码、Cookie、外层开发认证或包仓库凭证。Git、镜像层、前端产物不得含运行密钥、开发数据库或用户文件。
- 提供初始化、启动、检查版本、查看日志、重启、重置密码、更新及发布失败人工诊断说明。
- 挂载目录、证书卷、静态产物目录明确区分；普通更新不得执行删除数据卷的命令。

### Android 阶段扩展

[已确认的 Spec 005](005-android-text-loop.md) 从 Android 阶段引入独立 APK 发布和原生认证，不追溯增加本阶段的 Android 验收要求。

- Android 使用独立版本 tag、稳定签名和递增 versionCode，复用可信准入与确切 SHA 检查；签名凭证只提供给受控发布步骤，不进入 PR、缓存或公开制品。
- 开发原生请求的 Basic Auth 与 Bearer 冲突按 Spec 005 处理：Caddy 验证外层后将开发专用 Token 头转换为 Bearer，并移除临时头；无临时头不生成空 Bearer，不破坏开发 Web Cookie 流程。生产拒绝开发临时头。
- 区分外层拒绝与应用会话失效，所有新增敏感头纳入脱敏；具体映射通过真实开发 Web/Android 请求验证。

## 6. 待决与实施前检查

已确认 Apache-2.0 及公开 GHCR 后端/前端制品，无剩余许可选型问题。正式 LICENSE、版权声明、依赖许可兼容性检查及适用的第三方 NOTICE 保留义务在公开发布前落实；分发时保留必要声明，修改文件按许可要求标注。不以仓库公开代替许可履行。

实施时核实但不需猜定的环境项：仓库公开前安全检查、GitHub 规则实际能力、ARM64 runner 可用性及计费、完整开发域名、OCI 网络路径、ACME 验证、可用磁盘与构建/产物缓存配额。

审阅修订已明确旧客户端兼容策略、仅生产生效且持久的维护状态、版本绑定部署描述及迁移入口、确切 SHA 的可信发布检查。整份 Spec 已最终确认；可调参数如退出时限、健康检查间隔在实现前选定并记录。
