# Spec 002：桌面文件传输与容量控制

状态：原桌面版本已验收；单轮发送与串行交互及登录失效后清空等待项/File 引用已随 [Spec 007](007-implemented-flow-simplification.md) B/C 实现，稳定版桌面 Chrome 人工确认待完成。旧版证据见 [#33](https://github.com/nt1r/FileHop/issues/33)，不代表新行为的验收证据。

本文是文件传输的唯一行为契约；Spec 007 只组织改造。关联：[产品基线](../product.md) · [Spec 001](001-desktop-text-loop.md) · [Spec 003](003-server-file-management.md) · [路线图](../roadmap.md)。

## 1. 范围

消息工作区内多选、追加、串行流式上传及认证附件下载。文本发送独立。Android 复用同一文件发送语义，平台选择/保存见 [Spec 006](006-android-files.md)。

不做目录、分片、续传、内容去重、病毒扫描、跨刷新队列恢复、可靠后台传输、同一文件发送的后继重传或服务端强保证停止。

## 2. 选择与上传

- 多选及追加后按选择顺序自动发送，页面最多一个活动文件；等待项可移除，不预留服务器空间。
- 成功或明确失败后处理下一等待项；失败文件不自动重传，再发须重新选择并使用新 send_id。
- 每项显示文件名、大小、进度和结果；传输 100% 仅表示数据已发出，完整文件和消息提交后才显示成功。
- 单文件默认 100 MiB，可配置，允许空文件。认证限制查询供预检，服务器最终准入；限制未知或离线不启动新上传。
- 不限制扩展名/MIME；元数据不可信，实体使用安全唯一名称，不执行或同域内联展示上传内容。
- File 引用只在当前批次的页面内存保留，刷新/关闭不恢复，不自动重发。应用内导航不终结正常批次。

## 3. 结果未确认、中断与结束本轮

- 超时、断网、响应丢失均可能发生在服务端已提交之后，不能直接显示失败或成功。
- 当前发送结果未知时暂停后续项，显示“查询结果”和“结束本轮”；不建立自动查询/恢复调度，不自动重传。网络恢复也不自行确认或启动旧未知任务。
- 用户查询原 send_id：已成功返回原消息；已终结失败显示需重新选择；仍处理中或未找到保持未确认。单次 404 不是在途请求已取消的证明。
- 查询确认成功或终结失败后，可按正常队列规则继续等待项。服务端清理中已确定不能提交时可视为失败，但未清理实体仍占服务器额度。
- “中断传输”只 abort 当前本地准备/文件体请求，不调用服务端 stop、不撤回已提交内容。未知结果仍暂停队列；不显示“服务器已取消”。迟到准备不得触发被本地中断的内容发送。
- “结束本轮”明确确认后中断本地传输、清空全部上传队列及任务上下文，不再查询或协调旧任务。提示原文件可能已经或随后保存，重新选择前检查历史，重选可能重复；这是新操作，不是同次重试。
- 结束本轮不释放服务器预留、不证明旧写入者结束；之后可新建批次，由服务端额度和并发上限兜底。本页串行不承诺跨批次、跨页面或全实例最多一个服务器任务。
- 旧回调不能修改新批次或恢复已清除的任务；后续正常读取历史仍可展示真实已提交消息。
- 文件的单项“放弃确认”和“同次重试”移除；文本对应动作仍由 Spec 001 定义。

## 4. 登录与前后台

- 服务端在请求开始时鉴权，已认证的请求不因途中自然到期主动截断。
- 客户端发现登录失效则中断本地上传、暂停新操作、清空等待项及 File 引用；提示等待文件需重新选择。服务器仍可能保存已经接收的内容。
- 同页保留文字草稿和当前未确认文件发送的最小身份/展示信息，未登录时隐藏；重登后可手动查询或结束本轮，不自动查询、重传或恢复旧队列。
- 主动退出中断本地传输并清除全部敏感上下文，不发送服务器 stop。网络故障不承诺撤销凭证或上传成功结果；退出行为仍遵循 Spec 001。
- 页面隐藏暂停新调度，不保证已开始传输继续，也不因隐藏主动中断。认证有效且没有未知任务时返回前台可继续正常等待项。
- 更新按 Spec 004 先保存输入、结束传输，更新后刷新；不建设旧客户端兼容层。

## 5. 发送身份与接口

- 文件 send_id 与文本共享身份空间，固定类型、名称、大小、来源标签和 MIME。同标识不同元数据或跨类型复用拒绝。
- 每次文件发送只允许一轮内容传输；已失败、过期或终结的发送不因重放复活。再次选择产生新 send_id，可产生内容相同的另一条消息。
- 准备请求幂等，不重复预留；内容请求单写入者，重复请求不能并行写入、覆盖或创建第二条消息。已成功的结果长期可查询，不因文件删除丢失身份。
- 可保留现有单个 attempt_id 和内容路径以减少改造，不再存在前驱/后继链。它不是续传或允许失败重试的承诺。

| 接口 | 职责 |
| --- | --- |
| `GET /api/transfer-limits` | 认证能力快照，不预留空间 |
| `POST /api/file-sends` | 固定 send_id、单个 attempt_id 及元数据，幂等准备和原子预留 |
| `GET /api/file-sends/{send_id}` | 手动查询当前发送及已成功消息，未找到不证明取消 |
| `PUT /api/file-sends/{send_id}/attempts/{attempt_id}/content` | 单轮流式文件体，完整保存并提交后成功 |
| `GET /api/files/{file_id}` | 认证附件下载 |

`POST .../attempts` 后继创建和 `POST .../stop` 退役，不维护停止早于准备的持久标记。退役请求拒绝且不得静默新建发送；更新时刷新客户端。旧控制数据的保留/迁移遵循 Spec 007，不能因此重激活历史任务。

认证矩阵沿用 Spec 001：Web Cookie 写操作验证 Origin，未来有效原生 Bearer 不强制 Origin，混合凭证拒绝。先验证身份、元数据及准入，再读取文件体；代理不无界缓存。准备响应丢失时保留身份供查询，不自动生成另一身份发送。

限制快照仍提供 `max_file_size_bytes` 和 `upload_total_timeout_seconds`；后者范围 1–4,294,907 秒，XHR 加 60 秒确认余量后转毫秒，避免溢出。服务器准入使用当前限制，快照不是资格保证。

## 6. 容量与超时

- 总文件额度默认 1 GiB，可配置。原子预留申报完整大小；活动预留、已保存及待清理占用互不重复。空间不足明确拒绝，不无限等待。
- 实际字节数必须等于申报值；超额、不足或磁盘写入失败不得提交。传输不持有数据库长事务，内存不随文件体线性增长。
- 检查磁盘余量并处理运行时 ENOSPC。旧写入者结束、实体安全清理后才释放预留；客户端中断、结束本轮、退出均不能提前释放。
- 每个客户端串行不能替代服务器并发准入及资源背压；多个页面和未确认旧批次仍可能同时占用。
- 准备未开始默认 2 分钟回收；上传无进展默认 2 分钟、总期限 30 分钟；失败清理后台重试。参数可配置。
- 上传总期限限制接收及进入提交前的资格；进入持久化提交后，不因客户端中断或总超时粗暴取消。取消接收后也须等待底层写入退出，才能清理实体并释放预留。
- 保留现有期限分工：JSON 控制请求 15 秒；代理连接默认 5 秒、文件体发送完后的首响应等待默认 60 秒；不使用 JSON 短超时截断持续上传。客户端超时只产生未知结果。
- 下载读盘及背压无进展期限默认 120 秒，不设截断持续进展下载的固定总期限。浏览器最终落盘由浏览器管理。
- 调低额度不自动删文件；已有预留继续计费，新发送重新准入。重启先协调残留再接收新上传。

## 7. 文件持久化与下载

- 临时和正式实体同一文件系统、安全名称、排他创建；完整接收后持久写入/移动及必要目录同步，再以短事务提交消息、元数据、成功身份和占用转换。
- 文件系统与 SQLite 不是一个事务。无成功记录的遗留上传失败清理，不在恢复时补消息；有成功记录则保留文件和原结果。已确认成功后不因响应丢失删除消息。
- 成功记录对应实体缺失/异常时保留历史和身份，下载明确失败，不返回空文件、不自动重发或释放占用；按 Spec 003 显式管理。
- 只清理受管文件，确认没有旧写入者；全局存储故障不是所有实体消失的证明。单后端实例及启动恢复保护保留。
- 下载必须鉴权，使用安全附件名、`Content-Disposition: attachment`、`nosniff` 和默认 octet-stream，流式响应，不完整缓冲为 Blob。
- Web 可先探测可识别错误，但不承诺获知浏览器最终保存结果。
- 活动下载拒绝删除、接受删除后拒绝新读取，仍由 Spec 003 负责。

### 共享消息契约

- 消息用 `kind: TEXT | FILE` 区分类型。公共字段 `id`、`send_id`、`source_label`、`created_at` 保持 Spec 001 语义：消息 ID 为十进制字符串，发送标识不属于某次登录，时间为服务器确认保存时间。
- TEXT 包含 `text`；FILE 不包含 `text`，包含 `file_id`、`file_name`、`file_size`（字节数）、`file_mime`、`file_state`、`state_version`。文件名与 MIME 仅为元数据；文件状态枚举、版本编码及合并规则由 Spec 003 定义。
- 文件成功提交加入既有消息顺序；历史分页及增量游标沿用 Spec 001，不按本地选择顺序或文件修改时间排序，不把 FILE 当作空文本。
- `GET /api/sends/{send_id}` 对成功文件发送返回原消息及当前文件状态，删除实体不重建消息或文件。未提交详情由 file-sends 接口查询；未找到成功消息不证明原发送不会随后提交。
