# FileHop 第一版产品需求基线

状态：已确认。本文记录第一版的长期产品规则与约束，不是实现步骤或完整 API 设计。

相关文档：[领域术语](../CONTEXT.md) · [交付路线图](roadmap.md)

## 1. 定位与目标

FileHop 是轻量、自托管、面向个人的跨设备文本与文件交换工具，不是网盘、目录同步系统或唯一备份。

核心使用路径：桌面 Web ↔ 自建服务器 ↔ Android 原生应用。所有数据经服务器存储和交换，不做设备间直接投递。

可用性优先于技术探索。桌面 Web 是中间交付点，Android 完成后才覆盖电脑与手机的核心闭环。Wasm 等探索不计入核心项目完成条件。

## 2. 用户与客户端

- 单个实例服务单个用户，无公开注册，不承诺多用户能力。
- 通过服务端显式管理命令初始化数据库、受管存储身份和唯一账户，遵循 Spec 001；正常启动不得因数据缺失而自动创建替代实例。
- Web 仅承诺桌面浏览器使用，不保证手机浏览器体验。
- 手机端使用 Kotlin + Jetpack Compose 原生 Android 应用。
- Android 首次配置单个 HTTPS 域名根地址，默认正式域名；确认后不提供应用内切换，更换需清除应用数据并重新配置，会删除应用管理的本地副本。不做多服务器归属或实例检测、HTTP 或证书校验绕过。
- Android 使用 GitHub Release 签名 APK 手动安装更新；正式版保持稳定签名，开发版独立 application ID，数据隔离。
- 初始负载为少量设备并发，日常文本与文件交换。
- Web 仅承诺验收时最新稳定版桌面 Chrome，记录实际测试版本，不承诺其他浏览器或所有桌面操作系统组合。Android 最低支持 Android 10（API 29），至少验收最低版本及一个较新版本。

## 3. 消息流与文本

- 所有已登录客户端共享同一条私人消息流，不选择目标设备。
- 初期只有文本消息和文件消息；每次成功发送产生一条消息。
- 发送成功仅表示服务器已可靠保存，不承诺其他设备在线、接收或阅读。
- 默认展示最近消息，可分页加载更早记录。
- 文本为纯文本，保留换行，支持主动复制；默认不自动覆盖剪贴板。
- 文本上限为 64 KiB UTF-8，即 65,536 字节。
- URL 按普通文本显示，不抓取链接内容；不渲染 HTML 或 Markdown。
- 同一次发送重试不得重复创建消息；这不代表相同文本或文件内容不能再次发送。
- 不支持消息编辑、文本消息删除或历史清理。

### 来源标签

- 使用可读的来源标签，例如“办公室 Chrome”或“我的手机”。
- 默认提供粗略客户端名称，允许填写便于辨认的标签。
- 不采集硬件指纹，不承诺识别物理设备；标签不参与权限判断。
- 消息保留发送时的标签，之后改名或重新登录不改变旧消息显示。

## 4. 文件传输

### 上传与成功语义

- 单文件上限初始为 100 MiB，即 104,857,600 字节，允许通过配置调整。
- 桌面 Web 支持一次选择多个文件及追加选择，选中后自动上传，不额外点击确认；不支持目录上传。每个文件独立产生一条消息。
- 单页面最多同时传输 3 个文件，其余在页面内等待并自动接续；等待项不预留服务器空间，可单独移除。队列不跨刷新恢复，不限制独立的文本发送。
- 每个文件独立显示进度、结果和停止操作。停止不等于撤回：已提交则保留消息，无法确认则显示结果未确认；数据发送达到 100% 后仍需等待服务器提交确认。
- Android 同样支持多选、追加、自动上传及最多 3 个活动上传，等待项在进程内保存，旋转不丢失，进程终止不恢复。只保证前台传输，后台暂停启动新任务，不主动取消已经开始的传输。
- 使用普通 HTTP 流式上传与下载，服务端不得将整个大文件加载到内存后再写入磁盘。
- 上传先写临时文件；只有完整保存文件并成功提交记录后，才产生共享文件消息。
- 上传中的进度只在发起端展示，不进入共享历史。
- 服务器尚未成功提交的上传，中断或失败后不产生文件消息，服务端清理遗留临时数据。
- Web 上传由页面展示进度与错误；Web 下载允许由浏览器原生下载管理器展示进度和结果，页面处理能够识别的请求错误，不承诺获知最终本地保存结果。
- Android 在应用内展示上传、下载进度与结果。传输失败允许用户重新尝试，不做断点续传。
- 若服务器已成功提交但客户端未收到成功响应，保留文件消息；客户端显示结果未确认，而不是断言发送失败，并通过结果查询或同次重试确认结果。同次发送的重试须避免重复消息。
- 只保证前台传输，不保证隐藏页面、Android 切后台或锁屏后继续完成；不要求主动取消已经进行的传输。

### 文件记录与存储

- 保存原始文件名、大小、文件类型、上传时间、来源标签及唯一标识。
- 实体存储名称使用 UUID、ULID 等安全唯一标识，不直接使用原始文件名。
- 文件下载必须经过身份认证。
- 文件默认不自动过期；用户通过服务器文件页清理空间。

### 容量

- 应用服务器文件存储额度初始为 1 GiB，即 1,073,741,824 字节，可配置。
- 已占用空间加本次上传将超过额度时，明确提示并拒绝，不允许先超额再处理。
- 文件开始上传前，服务端按申报大小原子检查并预留完整额度；空间不足明确拒绝，不自动等待空间。传输过程不占用数据库长事务。
- 实际接收字节数必须与申报大小一致；临时数据包含在原预留内，不重复计算。同次重试不能重复占用额度，也不能同时写入同一上传。
- 临时文件、并发预留和待清理实体均须计入容量约束；未实际清理的空间不提前释放。不采用全实例只允许一个活动上传的限制。
- 检查磁盘可用空间，并正确处理检查后仍发生的磁盘不足。
- 不自动删除旧文件以腾出空间。
- 存储额度主要限制文件上传；实际磁盘不足也可能导致文本等写入失败，须如实提示。
- 提供基本的文件空间用量展示。
- 此额度不包含对整台 VPS 总占用的承诺；数据库、日志、容器镜像和操作系统仍需额外空间。

## 5. 文件管理与删除

### 服务器文件页

- 只管理经 FileHop 上传的文件，支持列表、基本信息、下载及单个删除。
- 不是 VPS 文件管理器，不暴露任意目录，不支持任意文件操作、目录浏览或文件夹管理。
- 服务端接受删除请求后，文件不再可用，所有客户端不能继续发起该文件的下载；服务端负责删除 VPS 上的实体。
- 对应文件消息保留名称、大小等历史信息。实体清理尚未完成时显示“删除处理中，空间尚未释放”；实体清理完成后标记“服务器文件已删除”。状态及查询规则遵循 Spec 003，具体视觉布局在实现中确定。
- 删除不影响任何设备已下载的本地副本。
- 若实体清理暂时失败，服务端重试；文件不能因此恢复为可下载状态，也不能向用户表示实体已删除或空间已释放。只有实体清理完成后才释放对应额度。
- 其他客户端在手动刷新或重新进入列表时校正状态，不承诺实时删除同步。
- 不提供回收站、恢复或批量清理。
- 文件正在下载时拒绝删除，提示下载结束后重试，不进入删除流程、不排队自动删除。“正在下载”以服务端持有活动读取句柄为准，不承诺跟踪浏览器最终落盘；具体裁决及状态规则见[已确认的 Spec 003](specs/003-server-file-management.md)。

### 本地副本

- Web 负责下载，本地文件交给操作系统文件管理器管理。
- Android 提供本地下载页，管理应用专属持久目录中的副本，支持打开、单个删除；卸载或清除应用数据会删除副本，不参与自动备份/迁移，不提供公共目录另存或导出。
- 每次主动下载可创建独立副本，展示名称冲突加数字后缀，不覆盖旧文件、不检测旧文件是否修改。同一服务器文件正在下载时不重复启动，完成后允许再次下载。
- 退出保留完整本地副本，未登录或会话未验证时不展示本地管理内容；服务器删除不影响副本。界面登录限制不等于文件加密，不承诺撤回其他应用已读取的数据。
- Android 通过系统文件选择器选择上传文件；本地下载可通过系统授权方式打开。
- 删除本地副本不影响服务器或其他设备。
- 不扫描整个手机文件系统，不跨设备管理本地文件。

## 6. 前台同步

- 使用 HTTP 增量拉取，不依赖 WebSocket 或 SSE。
- 客户端在前台可见时每 10 秒检查新增消息。
- 打开或重新进入页面时刷新，提供手动刷新。
- Web 页面隐藏或 Android 进入后台后，停止常规定时轮询。
- 网络失败有提示，并退避重试，不持续高频请求。
- 10 秒是检查间隔，不是网络异常时的送达保证。
- 手动刷新或重新进入列表时，校正服务器文件删除等已有记录状态。
- 增量游标、历史分页与状态校正分别遵循 Spec 001、003；仅获取新增消息不能替代状态校正。
- 不承诺后台接收、系统通知、未读状态或送达回执。

## 7. 认证与安全

- 用户名与密码登录，密码采用 Argon2id 等安全密码哈希，不明文存储。
- Web 使用安全 Session Cookie，设置 Secure、HttpOnly、SameSite；写操作需要适当的 CSRF 防护。
- Android 使用独立、可撤销的原生 Bearer 凭证，遵循 Spec 005；共享接口按 Spec 001 的认证矩阵区分 Web Cookie 的 Origin 防护与原生凭证认证。
- 登录从成功时起固定有效 12 小时，不自动续期；到期后的请求重新认证。
- 请求开始时验证凭证，已经通过认证的传输不因途中自然到期而主动截断。
- 支持退出当前登录。
- 提供服务端管理命令重置密码并撤销所有现有登录；不做按设备远程退出界面。
- 登录失败有节流措施。
- 所有公网数据传输使用 HTTPS，消息、文件与相关管理接口均须鉴权。
- 文件路径不使用未经信任的用户输入，防止路径穿越；原始名称和实体名称分离。
- Rust 后端不直接暴露公网端口。
- 敏感配置不提交 Git，开发与生产数据隔离。
- 服务器端文件允许明文存储；HTTPS 不等于静态数据加密。不做端到端加密。

## 8. 技术与部署约束

| 模块 | 基线方案 |
| --- | --- |
| 桌面 Web | React + Cloudflare Kumo |
| Android | Kotlin + Jetpack Compose |
| 后端 | Rust + Axum + Tokio |
| 数据库 | SQLite + SQLx，无独立数据库服务 |
| 文件存储 | 服务器本地文件系统，实体与业务元数据分离 |
| API | HTTP + JSON，文件流式传输 |
| 部署 | Docker Compose |
| 公网入口 | Caddy，自动 HTTPS、证书管理，仅开放公网 TCP 443，不承诺 HTTP 跳转 |

- 正式域名：`https://transfer.hammerbilly.top`。
- 公网 Web 入站通过 Oracle Cloud 网络规则仅开放 TCP 443，不开放 80，不要求修改宿主防火墙或既有 SSH 管理入口；仍须验证端口映射与实际网络可达性。
- 开发和生产同 VPS、独立应用栈及数据，共享独立 Caddy 入口。所有 CI 检查和发布构建使用 GitHub 托管 runner，不使用 VPS self-hosted runner。
- 仓库决定公开；默认分支为受保护的 dev，个人分支经 PR 进入 dev，仅本仓库 dev 可经 PR 合并至受保护的发布分支 main。版本 tag 触发产物构建并保存至 GHCR；生产由操作者在 VPS 手动执行脚本部署，Actions 不主动连接 VPS。
- 允许短暂维护窗口；部署失败人工处理，不承诺自动回滚。仓库公开前须检查完整历史中的敏感信息并落实 Apache License 2.0（Apache-2.0）许可；GHCR 后端镜像与前端静态制品决定公开，运行密钥与用户数据不得进入发布产物。
- Web、`/api/*` 和 `/api/files/*` 同域访问。
- Caddy 提供 React 构建产物，并通过内部网络反向代理到 `backend:8080`。
- 后端监听 `0.0.0.0:8080`。
- 容器内部数据库路径：`/data/database/transfer.db`。
- 容器内部文件目录：`/data/files`。
- 开发与生产均用 Compose，保持核心路径、端口和服务访问契约一致；允许开发热更新等环境差异。
- 开发宿主目录使用 `data-dev/database`、`data-dev/files`，不得与生产混用或提交开发数据。
- 生产可使用 `/opt/transfer/data/database`、`/opt/transfer/data/files` 挂载；应用不感知宿主路径。
- 通过挂载、配置、域名和密钥区分环境；生产不强制存在独立的前端运行容器。
- 开发者远程连接作为开发机的 VPS；使用独立的 `transfer-dev` 开发域名，完整域名待配置。Caddy 管理证书和 HTTPS，浏览器仅访问同域 443，前端开发服务及后端通过内部网络接受反向代理。热更新若使用 WebSocket，同样经同域 WSS 443，不属于业务消息同步。

## 9. 运维与风险边界

- 数据应在正常服务重启和容器重建后保留，提供运行、部署与更新说明。
- 本版不提供备份脚本、恢复流程、恢复演练或自动异地备份，不以其作为交付条件。
- 服务器或数据目录损坏时，不承诺找回历史与文件；已下载到客户端的副本不受服务器故障影响。
- FileHop 不作为用户文件的唯一备份。

## 10. 明确不在本版范围

- 手机 Web 适配、PWA、离线使用。
- 多用户、公开注册、OAuth/OIDC、二维码绑定或登录、完整设备管理。
- 通用 VPS 文件管理、目录同步、文件夹上传。
- 消息编辑、文本消息删除、历史清理、搜索、富文本、图片预览、链接卡片。
- Android 系统“分享至 FileHop”或分享导出入口。
- 后台可靠传输、后台同步、通知、WorkManager、SSE、WebSocket。
- 分片上传、断点续传、秒传、文件内容去重、单文件内部并行传输优化；桌面 Web 的多文件并发上传不在此排除范围。
- Wasm、客户端文件处理、端到端加密。
- 备份恢复、高可用。

上述能力不是未完成的承诺。未来如需增加，另行确认需求和交付范围。

## 11. 文档与 Spec 的职责

- 本文维护产品规则和边界；`CONTEXT.md` 只维护术语。
- 路线图维护交付顺序和退出标准；[测试与交付质量原则](testing.md) 维护测试分层、风险优先级及验证依据，不重复各 Spec 的验收清单。
- 一个可交付切片对应一个主 Spec Issue，包含场景、范围、非目标、行为、失败场景、验收标准、依赖和待决问题。
- 不为每个阶段另写重复需求文档；不把详细验收规则在 Issue 与文档之间双份维护。
- 先细化近期 Spec，远期只保留概要；API、数据结构、容量实现等随对应 Spec 决定。
- 改变已确认的产品规则时同步更新本基线，Issue 保留变更背景。
