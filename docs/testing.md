# 测试与交付质量原则

状态：已确认的实施原则。本文提供后续实现与评审依据，不代表测试已经实现或通过。

关联：[产品基线](product.md) · [交付路线图与 Spec 索引](roadmap.md)

## 1. 目标与优先级

以适量、可重复的验证保障实际使用，不以测试数量或覆盖率百分比代表质量。优先防范：

1. 未授权访问、凭证泄露及开发生产数据混用。
2. 已报告成功的数据丢失、状态误报和升级破坏数据。
3. 重试重复创建消息，迟到请求或回调干扰新操作。
4. 并发额度漏算、临时文件及资源无界增长。
5. 桌面与 Android 的核心交换闭环不可用。

不重复定义产品行为。具体预期与边界以六份 Spec 为准，测试发现契约冲突时先澄清文档，不让实现中的偶然行为成为标准。

## 2. 测试边界与分层

测试可观察行为和稳定的公共边界，不依赖私有方法、内部调用次数或特定代码组织。实现每个切片前，明确它的测试边界及验收映射；测试应能在行为不变的重构后继续有效。

### 少量规则单元测试

用于独立、确定且容易出错的输入输出规则，例如文本字节限制、空白校验、地址规范化、安全名称和兼容范围判断。优先表格驱动及共享测试样例，不要求每个函数、组件或类都有独立测试。

### 后端集成测试为主

通过真实应用接口，使用真实 SQLite 临时数据库及真实临时文件目录，验证认证、幂等、分页、容量、状态迁移及恢复。大多数接口测试可进程内执行；仅需要网络断流或进程生命周期的用例启动真实监听端口或子进程。

不以 Mock 数据库、事务和文件写入代替存储正确性验证。允许可控时钟及定点错误注入，以稳定验证到期、写入失败等情况；断言优先从接口结果及存储边界的可观察效果得出，不锁死数据库表结构或内部协作方式。

### 少量客户端端到端测试

验证登录、跨会话文本交换、上传下载、删除及关键失败反馈等用户闭环，不在 UI 层重复全部后端边界用例。主路径连接真实后端；网络拦截可用于制造响应丢失和乱序，不将整套假 API 当作真实闭环证明。

Web 可采用 Playwright；日常 Chromium 自动化不能自动替代 Spec 要求的稳定版 Chrome 验收。

Android 将快速状态测试与少量模拟器/真机流程分开。旋转、进程终止、系统文件选择、外部打开、最近任务隐私和 APK 更新等平台边界需按风险选择自动化或人工验证，不追求全厂商矩阵。

### 部署冒烟与人工验收

使用隔离环境和一次性数据验证初始化、持久化挂载、迁移、维护切换及失败状态。真实 HTTPS、Oracle 网络配置、证书管理、Android 系统行为等保留必要的人工证据，不为个人项目建设复杂云测试平台。

生产部署后只运行明确的非破坏性检查。不得对生产数据库或文件目录执行故障注入、清理演练、磁盘填满或测试重置。

## 3. 并发、故障与资源验证

- 集中验证持久化关键边界：实体写入/移动、数据库提交、响应返回、实体删除及额度释放之间的失败。
- 使用少量定点注入覆盖分支，并以必要的真实进程强制终止验证重启恢复；普通异常返回不能代替崩溃验证。
- 重点测试同发送标识并发、容量争用、下载与删除、停止与提交及旧尝试迟到，不枚举所有调度交错。
- 使用可控时间、屏障和条件等待，不依赖任意 sleep 或实际等待完整登录有效期。
- 流式传输需以不同文件规模和受控并发验证内存/暂存约束，不只凭代码看起来使用流就认定满足要求；不强制引入长期压力测试平台。
- 故障钩子限于测试配置或受控测试边界，不作为公网调试接口发布。测试工具不能成为绕过认证或修改生产数据的后门。

## 4. CI 与交付门槛

所有 CI 使用 GitHub 托管 runner，权限、可信发布和缓存规则遵循 Spec 004、005。

- PR：运行格式、静态/类型检查及相关快速测试、后端集成测试和必要的端到端冒烟。
- 合入受保护分支：运行适合该切片的较完整回归，包括必要的迁移、恢复及客户端检查。
- 发布：检查绑定确切 Git SHA，并验证相应发布产物；不能把其他提交的成功状态或缓存命中当作本次通过。
- 阶段交付：核心闭环及高风险异常有证据，平台特有或部署边界按清单人工验收。

任务拆分时根据实际耗时和风险选择执行频率，不要求每个 PR 都跑所有平台全套测试。按变更筛选时须覆盖共享 API、认证和依赖变化影响，不能只按目录名跳过关键测试。

构建缓存仅用于加速；冷缓存应可正确构建。保留失败所需的有限日志和 trace，使用合成测试数据，避免截图、日志或制品泄露真实凭证和消息。失败不能靠反复重跑到绿掩盖；暂时隔离不稳定测试须记录原因、风险及替代验证，不能无声削弱发布门槛。

## 5. 与 Spec 的对应及完成判定

- 现有验收编号是需求来源，测试或人工记录可引用 `S002-F04`、`S006-F06` 等全局唯一组合；不另抄完整验收清单。
- 一项验收可由多个测试共同证明，也可由一项集成测试覆盖多个相关验收；不要求编号与自动化一一对应。
- 每个已交付切片应能指出核心及高风险条目的自动化证据，人工项记录环境、版本、操作与结果。尚未验证的限制须明示，不把文档已确认当作功能已验收。
- 已复现的缺陷优先增加能够失败的回归测试，再修复；无法稳定自动化时记录复现和人工检查方式。
- 采用纵向切片逐步增加测试；实现哪个功能，就补相应质量保障，不先搭建六份 Spec 的全部测试框架。

## 6. 明确避免的过度设计

不设置全项目 100% 覆盖率目标，不强求每个函数或组件测试，不大规模依赖 UI 快照，不在所有层重复同一组完整边界，不为测试拆出无实际用途的通用接口或插件体系。

暂不建设全浏览器/全 Android 厂商矩阵、混沌工程平台、长期压测平台、全面变异测试或模糊测试平台。覆盖率和性能数据用于定位风险，不是单独的交付结论；未来只有出现具体收益时再增加这些能力。

## 7. 首个切片的实施起点

Spec 001 优先建立：显式初始化与认证的集成验证、文本幂等/分页/持久化验证、两个浏览器会话交换文本的端到端流程、登录到期与未知发送结果的反馈验证，以及 Compose 重建的数据保留检查。

工具与具体用例随任务细化，不在原则文档中固定所有命令、实现结构或测试数量。后续文件、部署及 Android 能力沿用上述分层与风险原则。
