# 测试与交付质量原则

状态：按单人自用范围简化。目标是尽快得到可用工具，不以测试数量、覆盖率、验收表完整度或报告数量代表质量。

关联：[产品基线](product.md) · [路线图](roadmap.md)。具体业务契约由 Spec 定义；本文件决定验证的力度与频率。

## 1. 先防什么

提前防范未授权访问、凭证泄露、路径穿越、开发生产数据混用、写失败却报成功、升级破坏数据及无界资源占用。保留已经稳定的幂等、容量和清理恢复保护，不为减少行数重写已有协议。

布局、滚动细节、罕见操作组合、旧系统兼容和跨版本无缝体验，遇到实际需求或缺陷再完善。新功能先实现最小正常路径和必要失败反馈，不枚举所有调度交错、系统版本或故障位置。

## 2. 公共测试边界

- 后端通过 HTTP API、管理命令、真实临时 SQLite 和文件目录验证行为；不 Mock 掉存储正确性。现有测试继续保留。
- 客户端用少量真实后端浏览器流程及实际手机验证；网络拦截只制造必要故障，不在 UI 重复后端全部边界。
- CI 范围选择通过 `scripts/ci-scope.sh` 的命令行输入输出验证；不绑定脚本内部组织。
- 部署通过隔离 Compose 的启动、数据保留和必要升级冒烟验证。镜像构建不能代替启动，但不在每个小改动中重演全部部署。
- 纯规则适合少量单元测试；不要求每个函数、组件都有测试，不为测试引入通用接口、插件或故障平台。

沿用 Rust、TypeScript/Playwright 和 Bash，不为语言或目录整齐重写有效测试。Bash 使用一次性目录、唯一资源名及退出清理，核实路径归属；等待有期限，不用任意 sleep 猜就绪。测试工具不加入生产镜像或公开调试接口。

## 3. 故障、资源及迁移

只在认证、存储、传输、恢复等相关改动时补对应风险验证。已有故障测试保留，不要求每张票建立完整故障矩阵。大文件内存测量和代理长传输首次验证、相关风险变更或发布前执行，不作为普通 UI/文档改动的固定工作。

迁移必须验证已有数据保留，至少覆盖最近实际发布结构到目标版本；没有旧发布时验证初始化，不造全历史升级矩阵。失败不能自动清库、接受新 checksum 或谎报升级成功；遵循[迁移规则](../backend/migrations/README.md)。

破坏性验证只用隔离合成数据，禁止对生产填盘、杀进程演练、重置数据库或清理真实文件。生产检查只执行获得授权的非破坏性操作。

## 4. CI 与交付门槛

所有 CI 和正式构建使用 GitHub 托管 runner。

- PR → dev：格式、静态/类型检查、构建、现有后端测试及真实后端浏览器回归；纯文档白名单差异只跑范围与来源策略检查。
- PR → main、手动完整检查：上述检查加大文件资源测量、隔离 HTTPS 和容器冒烟。
- 合入 dev/main：不再自动重复运行整套 Application checks；已有 PR 来源策略 workflow 不变。相关环境风险改动在合并前手动运行完整检查，发布 PR 始终兜底。
- 正式发布：检查确定提交与实际产物的启动/必要升级路径，无秘密、不消费不可信 PR 的特权产物。发布流程尚待实现，不把检查镜像当正式产物。

不再维护细粒度构建路径分类表。代价是 dev 中的环境特有问题可能到手动完整检查或发布 PR 才发现；容器、代理、迁移和依赖变更应主动选完整检查。不以增加路径过滤平台解决此权衡。

既有浏览器回归暂保留，不为提速盲删；出现实际耗时或不稳定问题再按风险拆分。缓存仅加速，失败不靠自动重试掩盖。隔离不稳定测试须说明原因、风险和替代检查。

## 5. 与 Spec 的对应及完成判定

- 新切片能覆盖实际核心路径及高风险行为，即可交付自用；已知限制直接说明，不要求每个验收编号都有独立测试或报告。
- 未受改动影响的既有自动化和人工证据可复用。非业务变更不触发完整人工重验；真实 Chrome/HTTPS/手机验证集中在首次接入、发布或相关平台行为变更。
- 用户已确认可用的相同业务版本，不因后续只补测试或文档再次索取全套确认。没有执行的项目不标通过；撤销的需求注明范围变更，不伪造历史验收。
- 缺陷修复优先加能复现实际问题的针对性回归；简单体验问题可人工复验，不人为制造 red/green 或新增测试平台。
- Issue/PR 简短记录“改变了什么、检查了什么、还有什么限制”，CI 留执行日志。验收编号仅作定位，不复制完整 Spec，不新增按 Ticket 编号命名的仓库报告。
- 长期运行说明进入开发/运行指南；进度只在主 Issue 简短收口，路线图仅保留大阶段状态。已有证据充分时同步父票，不另开一轮验收任务。
- 对外内容遵循 [CONTRIBUTING 隐私清单](../CONTRIBUTING.md#public-content-checklist)，真实凭证、数据和机器细节不进入公开材料。

不要求 100% 覆盖率、多浏览器/多 Android 版本矩阵、长期压测、混沌工程、全故障注入或全面人工签字。安全和数据正确性的已知阻塞应修复；其他小问题先用起来，有实际问题再修。
