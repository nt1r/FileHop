# 数据库迁移维护规则

使用 SQLx migrations 管理结构，发布与更新见 [Spec 004](../../docs/specs/004-web-production-deployment.md)。

## 稳定命名与冻结

- 新迁移采用递增编号和行为名称，如 `0002_add_native_sessions.sql`；不按发布重置编号，不在发布前后重命名。
- 已有 `0001_next_release.sql` 保留名称，不为命名整齐改动历史。文件名不作为待发布标记，也不要求换成应用版本号。
- 进入 main 的迁移版本、文件名、SQL 内容冻结；后续变更增加迁移。没有数据库变更不增加空文件。
- 尚未发布且确实没有需保留的实例依赖时，可整理开发迁移；已有需保留的数据必须走新增升级路径，不能自动清库。

## 数据与 checksum

SQLx 用数字版本识别迁移并校验 SQL checksum。不手工改写 `_sqlx_migrations`、自动接受不同 checksum 或用重复初始化绕过升级失败。

账户、密码、存储身份和用户内容不是生产 seed。测试使用隔离临时数据库和合成数据，生产密钥不进 SQL。

初始化与升级分别验证：首次安装初始化；已有实例停止后用目标镜像执行独立迁移，并验证原消息、账户和文件保留。最近实际发布结构到目标版本足够，不建设全历史组合矩阵。迁移失败保留数据、停止更新并人工处理。

`sqlx::migrate!` 编译时嵌入迁移，`init` 仅执行初始化，普通 `serve` 不升级。独立 `migrate` 排他锁定实例，校验存储身份、账户和迁移历史，由 SQLx 拒绝 checksum 不符、dirty 或未知版本；失败保留数据，不修改 Caddy。调用及诊断见[开发指南](../../docs/development.md#已有实例迁移与内部检查)，执行前停止旧后端并核对目标镜像。需保留的旧开发库不能通过 `init`、清库或重写 checksum 更新；当前只有初始迁移，尚无已发布旧结构的跨结构升级证据。

发布记录版本、SHA 和产物 digest 即可，不重复维护完整迁移清单。实际执行以目标数据库的 SQLx 记录为准；镜像发布不代表数据库已经升级。
